# Browser-local workflow history

Each workflow is an independently versioned unit. Its stable identifier selects a repository under `/repositories/` in one shared LightningFS filesystem. Display-name changes do not move repositories. isomorphic-git receives that filesystem and repository directory explicitly; application code never writes LightningFS's IndexedDB records.

Each repository contains `.git/` and `workflow.json`. The working file is the authoritative persisted workflow content. Git commits hold historical snapshots. Serialize validated content with two-space JSON indentation and a trailing newline, preserving array order. Names, descriptions, nodes, node positions, edges and their operational configuration belong in the versioned unit. Viewport, grid snapping and connection appearance are editor preferences stored outside Git, along with undo/redo navigation state. Selection and measured DOM dimensions remain transient.

A separate application IndexedDB database, accessed through `idb`, holds the catalogue (`id`, `name`, `repositoryPath`) and editor metadata. It does not hold a second independently editable workflow copy. IndexedDB schema versions, the existing workflow document format versions and Git commit IDs have distinct purposes.

Autosave captures one snapshot per completed edit and serializes write/stage/commit work per repository. Structural actions are captured immediately, even while a preceding save is in progress. Typing is grouped until the field loses focus; dragging is grouped until the node is dropped. Explicit saves, leaving the workspace and page visibility changes flush unfinished edits. Preference-only changes are debounced and do not add Git commits. Retain an unacknowledged save attempt with its exact snapshot and expected revision. If catalogue finalization fails after Git commits, retry that same attempt before saving a newer draft; accepting the current repository head blindly would bypass stale-editor protection. Keep the newer editor draft intact during recovery. Expected revisions detect stale editors. Cross-tab Web Locks protect repository mutations; unsupported browsers report a storage error instead of writing unsafely. Recovery metadata must not become a duplicate content store. A new draft's first save records its initial state before its first edit, so the first added node can be undone without creating saved entries for untouched drafts.

Automatic commit messages describe the diff against the actual parent snapshot: named node additions, removals and moves, named connection endpoints, workflow details and node configuration changes. Group generated data panels with their owning operation when adding or removing it. Compute the message inside the repository write lock so queued edits and edits after Undo compare against the right parent. Keep explicit import and restore messages. For existing commits whose message is exactly `Update workflow`, derive the displayed description from immutable commit blobs; do not rewrite commits, references or working files.

Undo and Redo move `main` between existing commits and update the working file and index without creating another commit. A private `refs/workflow/redo` reference preserves the future while undone, including across reloads. A content edit after Undo preserves that future on the next available `stash-N` branch and creates a new commit on `main`, whose parent is the selected version. These are ordinary Git branches, not Git stash objects. Preference-only or unchanged saves retain the redo path. Explicit Restore still creates a new commit and retains the existing history.

History merges `git.log()` results reachable from `main`, preserved branches and the redo reference, deduplicated and ordered with children before parents. The dialog draws actual parent relationships and marks the current version; branch names and commit hashes are not displayed. Historical rows provide Restore version directly; the dialog has no preview button or JSON preview. Opening history does not alter the working tree. Remote transport, credentials, synchronization and general branch-management controls remain outside this decision.

A recovery journal distinguishes new commits from navigation. It records the intended revisions, next navigation state and any reserved branch name before mutating repository state. Commit creation uses a fixed parent, timestamp and unique `Workflow-Change` message trailer so retries cannot manufacture duplicate versions. The trailer distinguishes separate edits that recreate identical content from the same parent within one second, while keeping real timestamps; the UI omits it from the readable message. Catalogue updates and journal removal finish in one application database transaction. Older pending saves finish before navigation metadata migrates; migration preserves every legacy commit and rebuilds navigation from the existing first-parent history.

Existing `operations-flow-documents-v1` localStorage documents migrate into independent repositories without changing IDs. Migration must be retryable; remove the old workflow key only after successful durable migration. Palette and light/dark settings use a separate application settings IndexedDB database, outside Git; their legacy localStorage keys migrate on startup. Existing JSON import/export and nested workflow snapshot formats remain supported.

IndexedDB persistence is asynchronous. The editor awaits saves before changing workflows or workspace. It starts a best-effort save when hidden, and requests an unload confirmation while changes remain unsaved. Do not claim that starting a write during `beforeunload` makes it durable. Storage errors leave the draft available for retry/export.

Reference APIs: [isomorphic-git](https://isomorphic-git.org/docs/en/quickstart), [LightningFS](https://github.com/isomorphic-git/lightning-fs), and [idb](https://github.com/jakearchibald/idb).
