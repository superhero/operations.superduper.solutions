# Background usage recording

The application starts a dedicated metrics worker independently of Settings. An origin-wide Web Lock elects one recording tab; its BroadcastChannel distributes snapshots and 15-minute bars to other open app tabs. A waiting worker takes over when that tab closes. Memory observations describe the recording tab and its dedicated workers; storage observations describe the origin.

The worker requests `measureUserAgentSpecificMemory()` through an asynchronous Window bridge because Chromium does not expose that API in dedicated workers. Once it settles, the bridge reads the Window-only heap and localStorage counters, and the worker collects storage estimates, database record counts and repository sizes. Collection never overlaps itself. Unsupported or failed memory measurements still allow the other counters to be recorded, with a 30-second minimum cycle instead of a busy loop. Git and aggregation run in the dedicated worker; browser garbage collection, storage locks and resource contention cannot be eliminated by using a worker.

Calendar-aligned one-minute OHLC accumulators feed calendar-aligned 15-minute bars. Per-metric sample counts include only available finite observations; missing observations are not zeroes and empty intervals are not invented. A worker timer closes elapsed intervals even while a new memory request is pending. Only the current minute and current quarter aggregates remain in RAM; individual samples and finalized minute detail are discarded. Open tabs retain the latest live aggregate and completed unsaved bars for leader handoff.

Only completed 15-minute bars enter Git. The separate `v1/metrics` LightningFS database contains `/metrics`, with one immutable file per interval under `bars/YYYY/MM/DD/HH-mm.json`. A separate writer lock and a flushed journal recover interrupted writes without changing workflow history. Raw samples and one-minute bars never enter a Git object, preventing supposedly removed detail from remaining reachable in old commits. Identical retries do not create extra commits; conflicting intervals are reported. Saved 15-minute bars are retained without automatic expiry.

The chart renders saved candles and a visibly provisional current candle, with a metric-selection tree whose groups remain fully unfolded and tooltips for values and local-time intervals. The tree groups Memory, Processing, Storage and Git filesystem measurements; database, store and repository branches preserve the underlying metric keys. Sampling continues while Settings is closed. Dedicated workers stop when their page closes and may be throttled or suspended in background tabs; recording cannot continue when all app tabs are closed. Closing every tab before an interval is complete loses that unfinished interval, while completed Git history survives reloads. Git history, numeric metric keys and values contain no workflow content, database record values or attribution URLs.

A disposable `v1/metrics/cache` localStorage entry makes the latest metric cards and a bounded preview of completed history available synchronously at startup. It holds the latest storage and memory reports plus at most 96 completed bars, capped at 512 KiB of serialized characters. IndexedDB Git history replaces this preview when loaded, and fresh measurements replace the cached report. Starting or restarting the worker preserves the last known values while collection is pending. Cached observations never enter the aggregator as new samples, and unfinished bars are never cached. Invalid, unavailable or full localStorage cannot stop recording; settings and workflow persistence remain in IndexedDB.

The inline worker remains inside the single HTML deployment artifact. Cross-origin isolation headers are needed for native application-memory measurements. The worker's runtime shim supplies the `global` alias expected by LightningFS's text encoder without importing the page's HMR or error-overlay code.

Processing counters describe the recording tab: the combined count of its main JavaScript context and managed dedicated workers, with worker count also available in history. Register app-owned workers with `trackApplicationWorker` after successful construction and release them on termination, including errors and page lifecycle cleanup. A follower tab still owns a waiting worker. These sampled counts enter the same OHLC history; they do not claim to enumerate browser-internal or operating-system threads, and `hardwareConcurrency` is not a usage count.

A Window-only `PerformanceObserver` aggregates main-thread long tasks without polling or keeping raw entries. Each collection drains pending entries, reads and resets the counters, and sends long-task count, elapsed task time, blocking time beyond 50 ms per task, and longest task to the existing worker and OHLC history. The sample interval follows the memory-driven collection cadence. These durations describe main-thread stalls, not CPU usage; ordinary webpage APIs do not expose CPU utilization, CPU cycles or aggregate GPU utilization. Unsupported measurements remain unavailable rather than recording zeroes. Recorder teardown disconnects the observer.

Candle history records resource measurements, including memory and storage bytes, utilization, record counts, processing durations, and tracked thread counts. Database/repository totals, database versions, store/index counts, Git inventory/status counters, and persistence status remain dashboard metadata rather than sampled candle series. Existing saved intervals remain intact, but retired series are excluded from the selector.

Storage utilization remains in the dashboard instead of recording a percentage derived from usage and quota. The histogram hides a storage-type series only when its complete candle history matches total storage usage and the latest available estimate does not distinguish them. Different or incomplete histories remain selectable, and equal values in unrelated metrics are never treated as duplicates. Storage components continue to be collected so they become available if their usage diverges from the total.
