# Default service schemas

The application bundles 224 packs covering 37 providers, 27,120 HTTP operations
and 105 Codex JSON-RPC client methods, alongside the two examples. Manage them in **Settings → Schemas**. Installation
loads API descriptions locally; it does not contact provider APIs or supply credentials.

- Cloud collections contain 55 AWS, 52 Google Cloud and 13 Azure contracts, with

## Google Workspace and other Google products

The 24 additional contracts cover Google products outside the Cloud collection:

- **Workspace (19):** Gmail, Drive, Calendar, Sheets, Docs, Slides, Forms, Tasks,

  Directory/Reports/Data Transfer, Drive Activity and Drive Labels.
- **YouTube (2):** Data and Analytics.
- **Analytics (2):** Admin and Data.
- **Search Console (1).**

Names use `Google / Workspace / …`, `Google / YouTube / …`,
`Google / Analytics / …` and `Google / Search Console`. Drive groups its main
API, Activity and Labels contracts together. Existing Google Cloud and Gemini
packs keep their payloads and workflow identities.

These are APIs.guru conversions of official Google Discovery descriptions,
with a narrow, reproducible `google-oauth` build adaptation. The converted
snapshots can lag the current provider APIs; the source manifest records the
exact version and hashes and links to the corresponding official Discovery
document. Admin SDK uses all three separate Directory, Reports and Data Transfer
contracts. Analytics Admin/Data use the available `v1beta` conversions.

The conversion lists implicit and authorization-code OAuth grants together as
though two bearer credentials must be supplied. Both Google grants issue an
access token for the same API. `build/google-oauth-schema.mjs` collapses only the
known Google pair with identical scopes into the authorization-code scheme,
retaining every scope alternative, both original flow descriptions and
`x-upstream-security` provenance. Unexpected grant definitions or mismatched
scopes fail generation. Generic security validation still rejects conflicting
credential headers. This opt-in adaptation does not rewrite existing Cloud packs.

The contracts add 655 HTTP operations. Of these, 640 pass the current request
transport checks; 15 Gmail/Drive/Chat/YouTube operations retain an explicit
upload limitation: these converted contracts describe metadata objects under
binary media types rather than usable raw-file upload contracts. This classification does not
certify live account access or current provider behavior.

For private user data, bind an OAuth access token with the required scopes from
the vault to `Oauth2c`. A token is an access token, not an OAuth client secret or
API key. [Google authorization](https://developers.google.com/workspace/guides/auth-overview)
still requires the appropriate app configuration, user consent and, where
applicable, Workspace administrator permissions. These schema additions do not
implement Google sign-in, token refresh or service-account signing. Generic
[binary file transport](workflow-files.md) does not fix the converted Google upload contracts.

## FRED and ALFRED

FRED covers US and international economic data, not just a region. The Federal
Reserve Bank of St. Louis manages both FRED and ALFRED. FRED includes the 31 v1
economic-data endpoints, the v2 bulk-release observations endpoint and the four
existing GeoFRED endpoints. Existing FRED operation identifiers are retained.

ALFRED exposes the same 31 v1 economic-data endpoints as a separate catalog for
historical vintages and revisions. It uses the real `/fred` routes on
`https://api.stlouisfed.org`; there is no separate `/alfred` route or key.
Set `realtime_start` and `realtime_end` to a past date to retrieve data known on
that date, or use `vintage_dates` and `output_type` for observation revisions.
Without a historical period, most endpoints return the current vintage.

[Register a FRED API key](https://fredaccount.stlouisfed.org/apikeys), save it in
the vault, and select it for the operation's credential binding. The worker sends
v1 keys as `api_key` query parameters and v2 keys as bearer tokens. Public inputs
cannot override these parameters, and previews omit authentication values.
Both catalogs explicitly request JSON for structured workflow outputs. Observation
values remain strings because the API uses `"."` for missing values. V2 bulk
requests use `next_cursor` to retrieve subsequent pages; reduce `limit` for large
responses to stay within the worker's response-size limit.

The base v1 schema is community-maintained. The reproducible
`build/fred-schema.mjs` adaptation adds documented JSON response structures and
the official v2 contract; each economic operation links to its official API docs.

## Execution limits

Typed controls cover supported constraints. Advanced JSON schemas use a JSON
input with API-side validation. Unsupported authentication, serialization and
streaming transports remain visible with an execution limitation, except the
reviewed [OpenAI Responses and Ollama HTTP streaming](http-response-streaming.md)
profiles, which assemble one bounded terminal JSON result. Raw binary
bodies and individual multipart file fields are supported when declared with
`type: string`, `format: binary`; see [workflow files](workflow-files.md). AWS signing is
unsupported. OAuth access tokens use bearer transport; login, token refresh and
scope acquisition are outside this feature.

Telegram uses [private bot token connections](telegram-private-path.md). Its
server placeholder remains in the source; the worker resolves the selected vault
reference for the fixed Telegram HTTPS endpoint. Token-filled server URLs are
not executable. Other unresolved server placeholders remain blocked.

Browser CORS and local-network restrictions still apply. Docker needs an HTTP
endpoint because browsers cannot use its Unix socket. Ollama must permit the
application origin. Account-specific server placeholders need configuration.
No provider credentials are bundled.
